##### depth-gated-sizing-must-shrink-not-block.md

In this trading system (NIFTY/SENSEX straddle execution, `api_v2_main_29_07_wings_new`), any depth-gated execution path — entry sizing, exit sizing, wing sizing, or any future feature that walks the order book before submitting — must always search for the largest quantity the *current* L1-L5 book can fully guarantee at a price strictly better than the configured target, and submit that reduced size, rather than blocking indefinitely for the full originally-requested quantity to become executable.

This came up when a depth-authorization entry gate was built strictly all-or-nothing (reject the whole request if the complete requested quantity couldn't clear the target price), matching a test file's literal contract. In production this caused an entry to loop forever: a first-pass capacity check found the book could momentarily hold 100 lots, froze that size, and a later price-based check then demanded exactly 100 lots clear the target on every retry — but the book only ever supported a smaller size at any given instant, so the fixed 100-lot request could never clear and the trade never executed. The user's correction was explicit: "u have to fill till whatever depth is available not complete depth" — i.e., find and take the largest size that genuinely clears the target (never a blind "take whatever's available regardless of price"), rather than treating a smaller available size as a reason to reject and wait forever.

The reconciled design: an inner primitive stays strictly all-or-nothing for a *specific* requested quantity (useful for validating an already-decided size, e.g. right before broker submission), but a separate outer search layer binary-searches over lot counts against that same strict primitive to find the largest size that actually clears, and that reduced-but-proven size is what gets authorized and submitted. Any future depth-gated feature in this codebase should follow that same two-layer shape rather than only implementing the strict all-or-nothing check.

In this trading system the MTM exit targets (`exit_at_mtm`, `partial_sqf_at_mtm`) always fire when the trade's MTM is **at or above** the target value (`MTM >= target`). This holds for negative targets too: a target of -85000 means "exit once MTM has recovered to -85000 or better", not a stop-loss that fires when MTM falls below -85000. The user's stated safe range was roughly 65–645 contracts per order (with `lot_size=65`, that's about 1–10 lots).

The fix pattern used: introduce a per-order cap distinctly *smaller* than the broker's own general `max_order_qty` safety limit (which already exists to avoid outright exchange rejection but was still large enough, e.g. 1800, to allow an oversized single order through this particular code path), and split any outstanding quantity into multiple capped, lot-aligned pieces before generating replacement/child orders — never place the full remainder as one ticket. Any future order-generation or reconciliation code added to this codebase should follow the same pattern: compute a small per-order ceiling (on the order of 1–10 lots, not the broker's raw max), and split rather than submit large single orders.

# Live Straddle Trading Dashboard

This is a real-time, event-driven options trading system built with Python, FastAPI, and ZeroMQ. It is designed for automated straddle trading, delta-neutral hedging, and provides a live dashboard for monitoring.

## Architecture

The system is composed of several microservices that communicate via ZeroMQ for high performance and low latency:

-   **Main Application (`main.py`)**: The central hub, providing the REST API, WebSocket endpoint for the UI, and managing trade lifecycle events.
-   **Market Data Service (`marketdata_service.py`)**: Connects to the broker's market data feed (XTS), processes ticks, calculates option chains with Greeks, and broadcasts data via ZMQ.
-   **Order Reconciler (`order_reconciler.py`)**: A dedicated process to poll the broker's order book, reconcile order statuses, and manage verification jobs.
-   **Snapshot Service (`snapshot_service.py`)**: Computes and broadcasts detailed, real-time PnL, Greeks, and other metrics for each active trade.
-   **Order Book Service (`order_book_service.py`)**: Caches and serves the broker's order book to other services.

## Features

-   **Microservice Architecture**: Decoupled services for scalability and resilience.
-   **Real-time Data**: WebSocket and ZeroMQ for low-latency data flow from market to UI.
-   **Event-Driven Trading**: An event bus manages trading logic (hedging, stop-loss, square-off) in a prioritized manner.
-   **Delta-Neutral Hedging**: Automated synthetic future hedging to manage position delta.
-   **Configurable Automation**: Trade parameters and monitor settings are configurable per-trade.
-   **Persistent State**: SQLite database for storing trades and orders.
-   **Shared Memory**: High-speed inter-process communication for price and order data.

## 2. Trade lifecycle

Trade UID looks like `ny121026144500` = NIFTY, 12-10-26, entry 14:45:00.
A trailing letter (`...a`) is a duplicate for the same minute.

Statuses seen in code: `PENDING_ENTRY` -> `BUILDING` -> `ACTIVE`, then
`HEDGING` / `ROLLING` / `PARTIAL-SQF` / `SQUARING-OFF`, ending in `CLOSED_SQF`,
`CLOSED_SL`, `CLOSED_SL_BUILD`, `CLOSED_ROLL`, `PARTIAL`, `CANCELLED`,
`FAILED_FILTER`, `FAILED_BUILD`. `get_open_straddles` excludes terminal ones.

**Entry paths**
- `trading/config_builder.py` `build_with_config()` - "config build" /
  portfolio pending config. Runs as an asyncio task **in the main process**
  (not a child process). Waits for entry time (or LUT-stage windows), then
  calls `trading/builder.py` `build_straddle`. In NORMAL CONFIG MODE the LUT
  decision is **informational only** - it builds at entry time.
- `trading/monitors/entry_straddle_monitor.py` - price-threshold
  `entry_at_straddle` entry, runs in a dedicated per-trade child process.
- `trading/lut_basket.py` - separate LUT-basket engine (`/api/lut/*`); a
  config build never runs LUT-basket logic.

**Build** (`trading/builder.py`, ~5.6k lines): delta-neutral PE/CE sizing,
lot-by-lot depth-gated tranches (`lot_build.py`, `depth_authorization.py`),
chunking, retry reconciliation (`builder_retry_reconciliation.py`), protective
wings (`builder_wings.py`, wing % from config; wing legs are classed
`PROTECTIVE_WING` and excluded from PnL/greeks risk scope), ATM recovery.

**Monitors per live trade** (`trading/trade_manager.py`,
`trading/monitors/*`): SL, hedge, roll, square-off, TP, straddle-price,
`fast_exit_monitor.py` (1 s FAST_TP / FAST_ATM / FAST_MTM checks) and the
minute-end loop. Event priority: HEDGE(1) > SL(2) > SQF(3) > ROLL(4) > MON(5)

`POST /api/straddle/cancel-action/{uid}` sets an **in-memory** flag in

## 6. `GammaShort_Backtest_Final.py` - what it does

One script, one pass over per-day tick files, simulating the full "GammaShort"
book: at most **one current-week (CW) trade per day**, plus an optional
**next-week (NW)** trade on DTE1/DTE2 days. Results are in "normalised Rs" =
index points x 25000 / entry underlying.

Per day:
1. **Load** the day's CW expiry rows (nearest expiry >= trade date; NW =
   next expiry). Build a **1-second grid**: underlying = first print per
   second, seconds without an underlying are dropped.
2. **Per-strike arrays**: LTP / bid / ask forward-filled; IV solved by
   Black-Scholes (r=0, T=DTE/365) from the OTM leg's LTP, only in seconds
   where that leg printed (`IV_MODE="tick"`), then held. 30-second forward
   average of bid/ask is the option fill price; 3-second for futures.
3. **Signal** each minute 09:16-13:30 (expiry day to 09:59), using the last
   second at/before hh:mm:00: Build IV (weekend-adjusted), IV ratio
   (= Build IV / blended IDV 0.2/0.5/0.3), straddle ratio (yesterday straddle
   / today's ATM LTP straddle), normalised opening gap, ADJ band, DTE bucket.
4. **Filters**: straddle veto per DTE, Build-IV floor on DTE1/DTE2, event
   days (no entry before 09:18, size 1/3). Five stage LUTs (09:16, :17, :18,
   :19, 09:20+); first hit wins.
5. **Execution**: sell the ATM straddle at the 30-s average bid; **strike held
   all day, no roll**. Second-by-second synthetic-future hedge: minute-start
   trigger (75 % re-hedge) and intra-minute trigger (1.2x, fully neutral);
   DTE1/DTE2 use a |net delta| trigger instead of points-out.
6. **Exits (checked each minute)**: SL (16 bps expiry, else 14 bps), TP ramp
   by Build IV and DTE, TV, TV4, 14:57 IV-drop (DTE <= 1), else end of grid.
   Exit at the 30-s average ask.
7. **Costs**: fixed entry slippage per DTE + bps of hedge notional.
8. **NW leg** (DTE1/DTE2 only): one check at 09:21 if no CW trade by 09:20;
   09:16 snapshot features -> `NW_LUT.csv`; sell at 09:21, SL 15 bps on mid,
   re-hedge at |net delta| > 0.10, exit 15:15.
9. **Fixed-entry comparison**: also simulates entries at 09:16/09:17/09:18
   ignoring the LUT, recording what production would have said (LUT_ON /
   LUT_OFF / VETO / FLOOR / EVENT_PRE_0918).

Outputs (in `OUTPUT_BASE/run_<config-hash>/`): `days/*.pkl` (resumable),
`daily_log.csv`, `trades.csv`, `entry_time_pnl.csv`, `backtest_summary.xlsx`,
`config.json`. Changing any rule/table changes the hash and starts a clean run.

Header reference result (1,379 days 2021-01-01..2026-08-24, `backtest_files`
inputs): NW "live" 10,640.5 / MDD 144.4 / CW 713 + NW 71; NW off
10,216.7 / MDD 120.6 / CW 720.

CLI: `python GammaShort_Backtest_Final.py [--only YYYY-MM-DD,...] [--summary]`.
Env overrides: `GS_TICK_DIR`, `GS_LUT_DIR`, `GS_OUTPUT_DIR`, `GS_START`,
`GS_END`, `GS_WORKERS`, `GS_DAY_INPUTS`, `GS_NW_ENABLED`, `GS_NW_CHECK_MODE`,
`GS_FIXED_ENTRIES`, ...
Needs: Python 3 with `numpy`, `pandas`, `pyarrow`, `numba`, `openpyxl`.

## 8. Candidate issues spotted in the backtest (not yet measured)

1. **Back-fill look-ahead.** `strike_arrays` does `ffill().bfill()` on prices
   and IV. Seconds before a strike's first print take the first *later*
   value. Mostly harmless at 09:16+ for ATM, but can leak future IV/price into
   the 09:16 snapshot when the OTM leg has not printed yet.
2. **Forward-looking fills.** Option fill = mean of the next 30 s
   (`rolling(30).mean().shift(-29)`), futures next 3 s. This is by design
   (execution over 30 s) but means PnL assumes full fill at that average.
3. **Minute-grid exits.** SL/TP/TV tested once per minute on the second-grid
   sample, so intra-minute spikes are not stopped out as live fast monitors
   would.
4. **Event-day entry cost not scaled.** `gross` and hedge notional are divided
   by 3 on event days but `ENTRY_SLIP` is charged in full (conservative).
5. **Hard-coded step 50** (`ATMRef = round(U/50)*50`) - NIFTY only.
6. **Daily CSV lookups** swallow exceptions per row (`except: continue`), so a
   malformed day silently becomes "no_day_inputs".
7. **Underlying definition**: first print of the second of `UnderlyingLTP`
   for that expiry's synthetic forward, not spot.

What the backtest does
It replays the full GammaShort book, one pass over the daily tick files. Each day gets at most one current-week trade, plus an optional next-week trade on days with 1–2 days to expiry. P&L is in "normalised Rs" (index points × 25000 / entry underlying).

1. Prepare the day.

It reads that day's parquet, takes the nearest expiry on or after the date as current-week, and the next expiry as next-week.
It builds a 1-second grid where the underlying is the first print of each second. Seconds with no underlying are dropped.
Per strike it forward-fills LTP, bid and ask, and solves IV from the out-of-the-money leg only in seconds where that leg actually traded.
2. Decide entry. Each minute from 09:16 to 13:30 (to 09:59 on expiry day):

It computes Build IV (weekend-adjusted), IV ratio against blended IDV (0.2/0.5/0.3), straddle ratio (yesterday's straddle ÷ today's ATM LTP straddle), opening gap, the ADJ band and the DTE bucket.
It applies filters: a straddle-ratio veto per DTE, a Build-IV floor on DTE1/DTE2, and event days (no entry before 09:18, size ÷3).
It looks up five stage tables (09:16, :17, :18, :19, 09:20+). The first hit wins.
3. Execute.

It sells the ATM straddle at the 30-second average bid, and the strike is held all day with no roll.
It hedges every second in the synthetic future, either on points-out or on |net delta| (DTE1/DTE2).
4. Exit. Checked once per minute:

SL: 16 bps on expiry day, otherwise 14 bps.
TP: a ramp by Build IV and DTE.
TV and TV4 (thin option value).
A 14:57 IV-drop (DTE ≤ 1).
Otherwise end of grid.
Exit is at the 30-second average ask.
